# Verify GetFileShare's encryption yourself

Two things you can do here, both offline and without any GetFileShare code:

1. **Check the published test vectors** — works today. Proves the parameters we
   document are the ones the implementation actually uses.
2. **Decrypt one of your own files** — proves the object we store is
   ciphertext, and that your password alone opens it.

## Setup

```bash
pip install -r requirements.txt
```

Two dependencies, both widely used and unrelated to us:
[`argon2-cffi`](https://pypi.org/project/argon2-cffi/) and
[`cryptography`](https://pypi.org/project/cryptography/) (pyca). Python 3.9+.

---

## 1. Check the test vectors

```bash
python check_vectors.py
```

`vectors.json` is generated by `../scripts/gen-verify-vectors.mjs`, which
imports [`../src/cryptoPassword.js`](../src/cryptoPassword.js) — the module the
site ships — so the vectors come from the real implementation rather than a
description of it.

The checker re-derives every key with `argon2-cffi`, decrypts every ciphertext
with `pyca/cryptography`, and confirms two properties that are easy to claim and
easy to get wrong:

- a **wrong password is rejected** rather than producing garbage;
- a **chunk presented at the wrong position fails** — each chunk's
  authentication tag is bound to its index.

Vectors are checked by *decryption*, not re-encryption: AES-GCM uses a fresh
random IV per chunk, so re-encrypting never reproduces the same bytes.

## 2. Decrypt your own file

```bash
python decrypt.py report.pdf.enc
# Password: ********
# Decrypted 20,975,841 bytes -> report.pdf
# Matches the hash recorded at upload.
```

It needs two files: the encrypted object exactly as stored, and a small
`report.pdf.enc.meta.json` holding the salt, chunk size and plaintext size.

> **Not yet available on the site.** A "Download encrypted copy" option on the
> download page of password-protected shares will produce both files. Until it
> ships, the vector check above is the way to verify the implementation.

Open the `.enc` file in a hex editor first: it is noise. Then try the wrong
password — it fails outright, because AES-GCM authenticates before decrypting.

## The format

Enough to reimplement, review, or argue with. Source of truth:
[`../src/cryptoPassword.js`](../src/cryptoPassword.js).

```
Key derivation   Argon2id
                   memory       65536 KiB (64 MiB)
                   iterations   3
                   parallelism  1
                   output       32 bytes -> AES-256 key
                   password     UTF-8, never transmitted or stored
                   salt         16 random bytes per upload,
                                base64url without padding

Cipher           AES-256-GCM
                   IV           12 random bytes, fresh for every chunk
                   tag          16 bytes
                   AAD          UTF-8("chunk-<0-based index>")

Per chunk        [ IV 12B ][ ciphertext ][ GCM tag 16B ]      +28 bytes
Whole object     chunks back to back, in order, no header

Reassembly       size is the PLAINTEXT length
                   chunks   = ceil(size / chunkSize)
                   offset n = n * (chunkSize + 28)
                   length n = min(chunkSize, size - n*chunkSize) + 28
```

The chunk size is chosen by the server at upload and recorded in the metadata —
read it from there rather than assuming a value.

---

## What this proves, and what it does not

**Proves:** the stored object is ciphertext, genuinely AES-256-GCM under an
Argon2id-derived key; the key comes from your password and a public salt and
nothing else, so no server-held key exists that could decrypt it; and your data
is recoverable without us.

**Does not prove:** anything about the browser code that produced the
ciphertext. We serve that JavaScript, so a compromised build could upload
perfectly valid ciphertext and separately leak your password, and everything
here would still pass. See the [top-level README](../README.md#what-this-does-not-prove).

**Scope:** password-protected cloud uploads only. An upload without a password
is stored as-is. Direct (E2E) transfers store nothing, so leave no artifact.
